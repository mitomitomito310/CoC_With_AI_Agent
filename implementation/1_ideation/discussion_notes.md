# Discussion Notes

## 2026-07-24: AI Keeper方向性の拡張

### User preferences

- AIがKeeperを担当することは固定する。
- シナリオは1セッションごとにフォルダを分ける。
- シナリオ進行中にKeeper情報をリポジトリへ更新し、より正確なKeeper運営につなげる。
- ソロ限定ではなく、AIがNPC探索者を用意し、ユーザー1人でも複数人相当で遊べるようにする。
- NPC探索者の情報・ステータスをリポジトリに記録する。
- そのNPCしか知り得ない情報は、セッション中に不用意に出さない。

### Follow-up answers

- シナリオ形式は、まず1セッション完結の短編ミステリー寄りで進める。
- NPC探索者は、独立行動もできるほうが面白そう。キャラクター作成段階で自律度を選べる設計にしたい。
- 情報分離は、公開ログ / Keeper秘匿 / NPC個別知識 / キャラシの4分割を起点にする。
- 必要なディレクトリ構成はさらに検討したい。詳細はRequirementsフェーズへ申し送る候補にする。
- リポジトリ更新頻度は、シーン終了ごとを基本にする。
- 最初は最終AGENTS.md用の運営ルール設計から始める。
- サンプルシナリオ、NPC探索者テンプレート、その他必要設計の洗い出しはすべて必要。詳細化はRequirementsフェーズへ申し送る。

### Agent impression

この方向性は、AI Keeperを単なる進行役ではなく、リポジトリを外部記憶として使うキャンペーン運営者にする点がとても良い。特に、NPC探索者が独立行動できる余地と、NPCごとの秘匿知識を分ける発想が強い。ユーザー1人でも複数探索者のドラマや推理のズレを楽しめるため、CoCらしい不確実性と会話の厚みが出せる。

### Ideas to carry forward

- NPC自律度をキャラクター作成時に選ぶ。
  - 低: ユーザー補助中心。
  - 中: 提案や技能ロールを行う。
  - 高: 目的・恐怖・秘密に従って独立行動する。
- 情報アクセス層を分ける。
  - Public: ユーザーと場に共有済みの事実。
  - Keeper Only: 真相、未開示手掛かり、メタ構造。
  - NPC Knowledge: NPCごとの既知情報・誤解・秘密。
  - Character Sheet: 能力値、技能、状態、所持品。
- Requirementsフェーズへの申し送り候補。
  - シナリオ単位ディレクトリ構成。
  - NPCごとの秘匿情報ファイル形式。
  - Keeperが発話時に参照してよい情報のルール。
  - シーン終了時更新のテンプレート。
  - NPC独立行動の許可範囲。
  - ログ、状態、手掛かり、ハンドアウトの分け方。



## 2026-07-24: 本格CoC体験と設計フェーズへの分離

### User preferences

- NPC自律度は、個別に数値設定するより、キャラクターシートから自動的に決まる形がよい。後から微修正できればよい。
- NPCの隠し事は積極的に許可したい。冷めるような安全制限より、なるべくドラマチックな展開を目指す。
- シナリオは基本的に既存シナリオを読み込ませて遊べるようにする。自由生成も可能にするが、その場合も真相は事前固定にする。
- ディレクトリ構成の詳細は今のIdeationではなく、Requirements/Designフェーズへの申し送りにする。
- 最終AGENTS.mdの優先順位は、AI Keeperの発話ルール、リポジトリ構造と更新手順、NPC探索者の運用ルール、セッション進行テンプレートの順でよい。
- CoCルール再現度は厳密寄りを目指す。ダイスや判定はskillsやスクリプト化でテンポを維持しながら、本格CoC体験を目指す。
- ユーザー探索者は、最初は新規、後で継続対応にする。
- NPC探索者ではなくユーザー探索者は、本格CoCプレイ相当の手順でユーザーが作る。ただし誘導チャットやskillsで簡単に作れるようにする。
- セッション中のリポジトリ更新は、更新概要だけを見せる。システムメッセージだと分かる形式がよい。

### Agent impression

かなり燃える方向性です。本格CoCを目指しつつ、ダイス・判定・キャラ作成をskillsやスクリプトで支える方針は、重厚さとテンポを両立できる可能性があります。特に「既存シナリオを読み込ませる」「自由生成でも真相は事前固定」「NPCはキャラシから自然に自律度が出る」という組み合わせは、フェアな推理とドラマ性の両方に効きます。腕が鳴ります。

### Requirements/Design handoff candidates

- 既存シナリオ投入時のファイル配置、秘匿範囲、読み込み手順。
- 自由生成シナリオの事前固定テンプレート。
- 厳密CoC判定をテンポよく回すためのdice/skill/script設計。
- キャラクターシートからNPC自律傾向を推定するルール。
- ユーザー探索者作成を誘導するチャット手順と補助skill。
- システムメッセージ形式の更新通知テンプレート。
- ディレクトリ構成詳細。


## 2026-07-24: 版・入力形式・キャラクター意思の尊重

### User preferences

- 既存シナリオの読み込みは、まずテキスト/Markdown化されたシナリオを前提にしてよい。
- CoCルールは現時点での最新版を主軸にする。2026-07-24時点では、Chaosium公式サイトの現行商品導線が7th Edition Rules PDFsやKeeper Rulebookを掲げているため、7版を最新版として扱う。
- ユーザー探索者作成支援は、フル手順でありながら簡単に作れることを目指す。
- NPCの裏切り・単独行動・虚偽発言は、キャラクターに入りきった行動であり、理由を説明でき、記録して後から見返せるなら許可してよい。
- システムで過度に制約せず、物語内のキャラクターの意思を最大限尊重する。

### Agent impression

めちゃくちゃ良い方向です。特に「NPCの行動を安全な駒として制限しない」「なぜそのキャラクターがその行動をしたのかを説明・記録できるようにする」という方針は、CoCの怖さ、疑心暗鬼、後から読み返したときの納得感を一気に強くします。AI Keeperがリポジトリを外部記憶として使い、シナリオ真相・公開情報・NPC個別知識・キャラクター意思決定ログを分けて持てれば、ただの進行補助ではなく、かなり本格的な“記録が残るTRPG体験”になります。これはかなり面白く育てられそうです。

### Requirements/Design handoff candidates

- CoC最新版は7版として開始し、将来新版が確認された場合の移行判断ルールを設ける。
- 既存シナリオ取り込みは、Markdown/テキスト入力を最初の標準形式にする。
- ユーザー探索者作成はフル手順を維持しつつ、質問分割・自動計算・候補提示で簡単にする。
- NPCの重要行動には、キャラクター内理由、参照した情報、表向きの発言、秘匿動機、セッション後に見返せる記録を残す。
- NPC行動はシステム的禁止で縛るのではなく、キャラクター性・所持情報・恐怖・目的・倫理観に基づいて制御する。

## 2026-07-24: チャット入力のモード選択案

### User idea

- シナリオ進行の入口がチャットだけになるなら、ユーザー入力をそのまま受け取るのではなく、入力意図を選択肢で分けると面白そう。
- 例: 「私はこの扉を開けようと思う」はシナリオキャラクターとしての発話、「扉を破壊」はキャラクターとしての行動、別枠でGM/Keeperへ相談する選択肢を用意する。

### Agent impression

これはかなり相性が良いです。チャットだけでTRPGを進めると、ユーザーの文章が「キャラクターのセリフ」なのか「行動宣言」なのか「プレイヤーとしてKeeperに確認している」のかが曖昧になりやすいので、入口でモードを分けるだけで没入感と運用精度が一気に上がります。特にCoCでは、口に出した発言がNPCに聞こえるか、探索者が実際に危険な行動をしたか、メタ相談として扱うかが重要なので、この分岐はゲーム体験の中核になり得ます。

### Ideas to carry forward

- 入力前または入力後に、ユーザー意図を3モードで扱う。
  - Character Speech: 探索者がその場で発言した内容として扱う。
  - Character Action: 探索者が実行しようとする行動宣言として扱う。
  - Player to Keeper: プレイヤーからKeeper/GMへの相談・確認・メタ質問として扱う。
- 入口UIがチャットだけでも、Keeperは必要に応じて番号選択を提示できる。
  - 1: キャラクターとして喋る。
  - 2: キャラクターとして行動する。
  - 3: Keeper/GMに相談する。
- 曖昧な入力は、Keeperが勝手に確定せず「これは発言、行動、GM相談のどれとして扱いますか？」と確認する。
- 将来的には、入力文からモードを推定しつつ、危険・不可逆・公開発言になり得る場面だけ確認する形にできる。
- Requirements/Designでは、各モードが公開ログ、秘匿ログ、判定、NPC反応にどう影響するかを設計する。
